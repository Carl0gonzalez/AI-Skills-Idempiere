# Core Java standards

## Scope and authority

Use only for the iDempiere core repository. Read the target checkout's AGENTS.md, matching .agents/skills and PR template first. Their applicable instructions and the project's official documentation govern; this central adaptation is not a replacement for newer local rules. Resolve the exact release, JDK, build and database baseline rather than importing another release's settings. See [the pinned upstream policy](https://github.com/idempiere/idempiere/blob/75ad26081a1745ab64831567861ad8f9f6f78d36/AGENTS.md).
## Implementation rules

- Match surrounding style; use English identifiers/comments and the repository's GPLv2 header for new Java files. Avoid reformatting unrelated lines, warnings and unused imports.
- Prefer existing M* model APIs, then Query, then DB helpers, then JDBC when unavoidable. Bind values; use generated table/column constants when practical. Verify cache semantics before modifying a cached PO.
- For bulk changes, inspect target-version batch PO APIs and tests. Do not assume their availability or lifecycle equivalence on another release. Raw UPDATE bypasses PO hooks, events and change logs; use it only intentionally.
- Propagate the owning trxName through constructors, Query and DB. Never commit/rollback a transaction you did not create or mix null transactions into an active operation.
- Preserve tenant/org/role access; client filtering alone is not full role authorization. Use access helpers as required by the surrounding code.
- SQL must support PostgreSQL and Oracle. Prefer portable helpers; justify unavoidable database branches and verify each. Closing JDBC resources must follow the target convention and work on failure paths.
- Place PO invariants in the existing appropriate lifecycle methods or components. Use translated AD_Message/Msg text for user-visible output and compatible AdempiereException/CLogger APIs. No System.out, swallowed exceptions or secrets in logs.
- Never hand-edit X_*/I_* models. New AD records/DDL require human UI generation under the database skill.
- Preserve public/protected signatures using compatible overloads or deprecation. Intentional breaks require the developer's explicit decision, PR declaration and migration documentation. Follow the target serialVersionUID convention.
- Existing columns and default behavior may be used by plugins. Prefer an opt-in when changing behavior, with its AD/SysConfig generated by the developer. Discuss genuinely needed new dependencies because they affect OSGi and licensing.

## Review before completion

Search all callers in base, UI, processes and tests. Check other document types, currencies, accounting schemas, clients/orgs and both databases. Review document actions through the real document engine/workflow. List observable collateral scenarios and focused regression tests. A suspected vulnerability goes through the private Jira/security workflow, not a public description.

## Output

Explain the minimal correction, API/transaction/data-access decisions, caller impact, files, tests/build and unverified database/runtime paths. See [references/data-access.md](references/data-access.md) for review questions.
