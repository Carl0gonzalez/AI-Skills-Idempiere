# Core database and dictionary changes

## Scope and authority

Use only for the iDempiere core repository. Read the target checkout's AGENTS.md, matching .agents/skills and PR template first. Their applicable instructions and the project's official documentation govern; this central adaptation is not a replacement for newer local rules. Resolve the exact release, JDK, build and database baseline rather than importing another release's settings. See [the pinned upstream policy](https://github.com/idempiere/idempiere/blob/75ad26081a1745ab64831567861ad8f9f6f78d36/AGENTS.md).
## Non-negotiable core boundary

Do not create/edit SQL migration statements, core DDL, invented AD IDs/UUIDs or generated X_*/I_* sources. This includes repairing a generated migration by rewriting it. The developer uses UI migration logging and Centralized IDs; the agent specifies changes, reviews output and implements Java against verified generated metadata. Core sample-data migrations are generated by the developer too. These rules do not automatically prohibit authorized migrations in private plugins.

## Workflow

1. Detect required schema/AD changes early. Pause only the dependent implementation; continue independent diagnosis/design.
2. Give a precise UI specification: entity, table/column/message/process, reference, length, default, mandatory/updatable status, parent/link, window/tab/field placement and purpose. Do not invent IDs or use numeric placeholders as real values.
3. Guide the developer to request Centralized IDs, log in as System Administrator, enable Dictionary Maintenance and Log Migration Scripts, set the ticket comment and create/synchronize the objects through UI.
4. Ask for the generated PostgreSQL and Oracle files and regenerated models if columns/tables changed. Do not generate substitute scripts when these are missing.
5. Review with [references/generated-migrations.md](references/generated-migrations.md). Report unrelated statements, failed logged statements, inconsistent DDL and IDs of unclear origin; let the developer correct/regenerate them.
6. Confirm the test database destination and exact pending migration set before any authorized SyncDB application. On the database used to create dictionary records, those changes may already be applied; verify state rather than applying blindly.
7. Implement Java only against verified records/generated APIs. Include reviewed files with the code in the same ticket PR when publication is authorized.

## Output

Return the UI specification, generation prerequisites, reviewed files/findings, PostgreSQL/Oracle parity, model-regeneration state and applied-versus-reviewed status. Existing GardenWorld IDs may be looked up read-only for DictionaryIDs; never invent them.
